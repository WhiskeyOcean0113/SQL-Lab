## Why you need it {#why}

shop wants customers to rate and review products. None of the five tables has room for that, so it needs a new table, `reviews`: which product, how many stars, the comment, whether the reviewer is a verified buyer, and when it was written.

Until now every table already existed. This chapter starts designing tables yourself, and the first decision is what type of value each column holds.

## Core idea {#core}

### Creating a table

`CREATE TABLE` gives the table's name and each column's name and {{term:data-type}}:

```sql run
CREATE TABLE reviews (
  id          integer GENERATED ALWAYS AS IDENTITY,
  product_id  integer,
  rating      smallint,
  comment     text,
  verified    boolean DEFAULT false,
  reviewed_at timestamptz DEFAULT now()
);

INSERT INTO reviews (product_id, rating, comment)
VALUES (3, 5, 'Short and to the point.'),
       (5, 4, 'Loud but lovely.');

SELECT id, product_id, rating, comment, verified FROM reviews;
```

Like every change before, the table is undone when the run ends, so it no longer exists on the next run.

### A type is a set of rules

A column's type decides three things: which values it can hold, how values compare and sort, and which operations work on them. Compare "10" and "9" as text and as numbers, and you get opposite answers:

```sql run
SELECT '10' < '9' AS as_text, 10 < 9 AS as_number;
```

Text compares character by character, and "1" comes before "9". So quantities and amounts belong in numeric types and dates in date types; storing everything as `text` to save thought is a trap.

### Everyday types

| Kind | Types | Holds | Note |
|---|---|---|---|
| Integers | `smallint`, `integer`, `bigint` | Whole numbers | Ranges of about ±32 thousand, ±2.1 billion and ±9.2 × 10¹⁸; going beyond is an error |
| Exact decimals | `numeric(p, s)` | Amounts that must not drift, like money | p digits in all, s after the point; extra decimals are rounded |
| {{Term:floating-point|Floating point}} | `real`, `double precision` | Scientific values and measurements | Slightly inexact; never for money |
| Text | `text`, `varchar(n)` | Any text | `varchar(n)` allows at most n characters; more is an error |
| Boolean | `boolean` | Yes or no | `true`, `false` or NULL |
| Date and time | `date`, `timestamp`, `timestamptz`, `interval` | A date; a date and time; a moment with a {{term:time-zone}}; a duration | See Going deeper |

### Automatic ids and defaults

- `GENERATED ALWAYS AS IDENTITY` makes `id` an {{term:identity-column}}: leave it out when inserting and the database numbers rows 1, 2, 3 and so on. This solves the `max(id) + 1` problem mentioned in Chapter 7.
- `DEFAULT expression` gives a column a {{term:default-value}}, used whenever an insert leaves that column out. Above, `verified` defaults to `false` and `reviewed_at` to the moment of the insert.

## Syntax {#syntax}

```syntax
CREATE TABLE table_name (
    column_name data_type [ DEFAULT expression ] [ GENERATED { ALWAYS | BY DEFAULT } AS IDENTITY ] [, …]
)
```

```syntax
ALTER TABLE table_name ADD COLUMN column_name data_type [ DEFAULT expression ]
DROP TABLE [ IF EXISTS ] table_name
```

| Part | What goes there | Rule |
|---|---|---|
| `table_name` | The new table's name | Must not match an existing table |
| `column_name data_type` | A column's name and type | Required; columns are separated by commas, with none after the last |
| `DEFAULT expression` | The value used when the column is left out | Optional; without it, the default is NULL |
| `GENERATED … AS IDENTITY` | Let the database number the rows | Optional; integer columns only; `ALWAYS` forbids writing ids by hand, `BY DEFAULT` allows it |
| `ALTER TABLE … ADD COLUMN` | Adds a column to an existing table | Existing rows get the default in the new column |
| `DROP TABLE` | Deletes a whole table with all its data | `IF EXISTS`: no error if there is no such table |

The next lesson adds constraints such as `PRIMARY KEY` and `NOT NULL` after the column definitions.

The `CREATE TABLE` in Core idea, read against the shape:

- `id integer GENERATED ALWAYS AS IDENTITY`: `column_name data_type` plus automatic numbering.
- `rating smallint`: just a name and a type.
- `verified boolean DEFAULT false`: plus a default.

## Example {#example}

The task: create a `reviews` table for product reviews and insert two of them.

1. **List what to store.** An id, the product, the rating, the comment, whether it is verified, and when it was written.
2. **Choose a type for each column.**
   - Id: `integer`, generated by the database.
   - Product: `integer`, the same type as `products.id`, so the two can be joined later.
   - Rating: 1 to 5 stars, so `smallint` is plenty.
   - Comment: any length, so `text`.
   - Verified: `boolean`, defaulting to `false`.
   - Time: `timestamptz`, defaulting to now.
3. **Write the `CREATE TABLE`.** Commas between column definitions, none after the last.
4. **Insert two rows, leaving out the columns with defaults, and see what the database fills in.**

```sql run
CREATE TABLE reviews (
  id          integer GENERATED ALWAYS AS IDENTITY,
  product_id  integer,
  rating      smallint,
  comment     text,
  verified    boolean DEFAULT false,
  reviewed_at timestamptz DEFAULT now()
);

INSERT INTO reviews (product_id, rating, comment)
VALUES (3, 5, 'Short and to the point.'),
       (5, 4, 'Loud but lovely.')
RETURNING *;
```

The ids are 1 and 2, `verified` is `false`, and `reviewed_at` is the moment of the run (shown in UTC). The table is still loose: a rating of 0 or 99 goes in, and a product id can point at a product that does not exist. The next lesson closes those gaps with constraints.

## Variations {#variants}

**A length limit.** Going past `varchar(n)`'s limit is an error, not a silent cut:

```sql run error
CREATE TABLE labels (code varchar(5));
INSERT INTO labels VALUES ('Garden Tools');
```

`value too long for type character varying(5)`.

**Precision and range.** `numeric(5, 2)` goes up to 999.99. Extra decimals are rounded; extra whole digits are an error:

```sql run
CREATE TABLE prices (amount numeric(5, 2));
INSERT INTO prices VALUES (999.994), (12.345)
RETURNING amount;
```

Inserting `1234.5` instead fails with `numeric field overflow`.

**Adding a column to an existing table.** Give products a weight; the 16 existing rows are NULL in the new column:

```sql run
ALTER TABLE products ADD COLUMN weight_kg numeric(6, 2);
SELECT id, name, weight_kg FROM products LIMIT 3;
```

With a `DEFAULT` on the new column, existing rows take that default instead.

**Dates plus durations.** An `interval` is a length of time, and can be added to dates and times:

```sql run
SELECT DATE '2024-07-01' + INTERVAL '3 days' AS due;
```

## Going deeper {#deeper}

**Floating point is inexact.** `double precision` stores decimals as binary approximations, so `0.1 + 0.2` is not `0.3`:

```sql run
SELECT 0.1::float8 + 0.2::float8 AS float_sum,
       0.1 + 0.2 AS numeric_sum,
       0.1::float8 + 0.2::float8 = 0.3 AS float_equal;
```

`numeric` has no such problem; it is just slower to compute with. Store money and quantities as `numeric` or integers, and reserve floating point for values that are approximate anyway, such as scientific measurements.

**`timestamp` or `timestamptz`?** `timestamp` records only what the clock on the wall said, with no idea which time zone. `timestamptz` records a definite moment: input is converted using the zone given, and output is shown in the session's zone (UTC in SQL Lab):

```sql run
SELECT TIMESTAMPTZ '2024-07-01 10:00:00+08' AS beijing_ten_am;
```

10 a.m. in Beijing shows as 02:00 UTC. When users live in different time zones, use `timestamptz`. shop's `ordered_at` is a `timestamp`, with the convention that every value is UTC.

**`text` or `varchar(n)`?** In PostgreSQL they are stored and processed identically. Write `varchar(n)` only when you truly need a limit, such as for a country code. `char(n)` pads with spaces and is almost never wanted. Other databases weigh this differently; MySQL's `TEXT`, for example, has some restrictions.

**`ALWAYS` or `BY DEFAULT`?** `GENERATED BY DEFAULT AS IDENTITY` lets you write ids by hand, but the database's counter does not skip past them: after you write 10 by hand, automatic numbering still starts at 1 and sooner or later collides with 10. Unless you are importing data that already has ids, use `ALWAYS`. The `serial` common in older PostgreSQL tutorials is the old way of writing the same thing.

**Other types.** PostgreSQL also has `uuid` (globally unique ids), `jsonb` (JSON documents), arrays, range types and more. Each has its uses, but the types above cover most columns of most tables.

## Common mistakes {#mistakes}

**1. Storing numbers as text.** A quantity stored as `text` sorts by characters, putting "10" before "9"; adding it up needs a conversion first; and values like "twelve" can creep in. Quantities, amounts and ids belong in numeric types.

**2. Money in floating point.** Prices in `double precision` add up to tails like 0.30000000000000004 that never balance. Use `numeric(p, 2)`.

**3. Writing an id into an `ALWAYS` identity column.**

```sql run error
CREATE TABLE tags (id integer GENERATED ALWAYS AS IDENTITY, name text);
INSERT INTO tags (id, name) VALUES (1, 'sale');
```

`cannot insert a non-DEFAULT value into column "id"`. Leave `id` out of the insert and let the database number it.

**4. An integer type that is too small.** `smallint` stops at 32767, so inserting 40000 fails with `smallint out of range`. Two `integer`s adding up past about 2.1 billion overflow too. When unsure, use `integer`; for counts that may grow very large, `bigint`.

**5. Ambiguous date formats.** Is `'01/02/2024'` 2 January or 1 February? It depends on database settings, and SQL Lab simply refuses it with `date/time field value out of range`. Always write ISO format, `'2024-02-01'`.

**6. A comma after the last column.** `CREATE TABLE t (a integer, b text,)` fails with `syntax error at or near ")"`. Commas separate columns, so none follows the last one.

## Summary {#summary}

- `CREATE TABLE name (column type, …)` creates a table; the type decides what a column holds, how it compares and what you can compute with it.
- Integers in `integer` or `bigint`, money in `numeric(p, s)`, text in `text`, yes/no in `boolean`, moments in `timestamptz`.
- Floating point is inexact, so not for money; never store numbers or dates as text.
- `GENERATED ALWAYS AS IDENTITY` numbers rows automatically, and `DEFAULT` sets the value used when a column is left out.
- `ALTER TABLE … ADD COLUMN` adds a column; `DROP TABLE` removes a table.
